# 휴숨 DB 설계 문서

휴숨 MVP는 현재 실제 DB를 연결하지 않고 mock 쉼터 데이터, 로컬 상태, CSV 분석 결과, 공공데이터 API fallback 구조로 동작한다. 이는 기말 평가용 MVP에서 핵심 UX와 데이터 분석 흐름을 빠르게 검증하기 위한 선택이다.

실서비스 단계에서는 쉼터 기본 정보, 시민 제보, 즐겨찾기, 사용자 맞춤 설정, 분석 결과, 공공데이터 API 캐시를 DB에 저장해 추천 정확도와 운영 안정성을 높일 수 있다. DB는 Supabase 또는 PostgreSQL 기반으로 확장 가능하다.

## 현재 MVP에서 DB를 붙이지 않은 이유

- 로그인, 사용자 계정, 권한 관리가 아직 MVP 범위가 아니다.
- 쉼터 추천 UX, 지도 fallback, CSV 분석 결과 반영을 먼저 검증하는 단계다.
- 실제 DB를 연결하지 않아도 mock 데이터와 로컬 상태만으로 홈, 지도, 분석, 즐겨찾기, 마이 탭 흐름을 시연할 수 있다.
- 공공데이터 API는 실패 가능성이 있으므로 MVP에서는 fallback 데이터를 함께 사용해 시연 안정성을 우선했다.
- API 키와 사용자 데이터를 안전하게 관리하려면 서버 또는 프록시 구조가 필요하므로, DB 연동은 실서비스 단계에서 진행하는 것이 적절하다.

## 실서비스에서 DB가 필요한 이유

- 시민 제보를 누적해 쉼터 운영 상태, 혼잡도, 냉방 상태를 지속적으로 보정할 수 있다.
- 사용자 맞춤 설정과 즐겨찾기를 기기 변경 후에도 유지할 수 있다.
- 공공데이터 API 응답을 캐싱해 호출 실패와 속도 문제를 줄일 수 있다.
- CSV 분석 결과를 지역별 위험도 데이터로 저장해 홈/분석/추천 화면에서 재사용할 수 있다.
- 관리자 검수, 잘못된 제보 필터링, 데이터 갱신 이력 관리가 가능해진다.

## 테이블 설계

### shelters

쉼터의 기본 정보를 저장한다. 통합대피소 API 또는 관리자 입력 데이터를 기반으로 지도 마커와 추천 후보를 구성한다.

| 컬럼 | 설명 |
| --- | --- |
| id | 쉼터 고유 ID |
| name | 쉼터명 |
| type | 쉼터 유형 |
| address | 주소 |
| latitude | 위도 |
| longitude | 경도 |
| open_hours | 운영 시간 |
| capacity | 수용 가능 인원 |
| cooling_status | 냉방 상태 |
| heating_status | 난방 상태 |
| wheelchair_accessible | 휠체어 접근 가능 여부 |
| water_available | 물 제공 여부 |
| source | 데이터 출처 |

앱 연결: 지도 화면 마커, 홈 최적 쉼터 추천, 쉼터 상세 화면의 기본 정보로 사용한다.

### citizen_reports

사용자가 쉼터 상태를 제보한 정보를 저장한다. 공공데이터만으로 알기 어려운 실제 운영 상태와 혼잡도를 보완한다.

| 컬럼 | 설명 |
| --- | --- |
| id | 제보 고유 ID |
| shelter_id | 제보 대상 쉼터 ID |
| operation_status | 운영 상태 제보 |
| crowd_level | 혼잡도 제보 |
| cooling_status | 냉방 상태 제보 |
| heating_status | 난방 상태 제보 |
| wheelchair_accessible | 접근성 제보 |
| risky_route | 위험 경로 제보 |
| created_at | 제보 생성 시각 |

앱 연결: 쉼터 상세 상태 정보와 추천 점수 보정에 사용한다. 예를 들어 최근 제보에서 혼잡도가 높으면 추천 점수를 낮추고, 냉방이 쾌적하다는 제보가 많으면 추천 이유에 반영할 수 있다.

### user_preferences

사용자 맞춤 설정 정보를 저장한다. 현재 MVP에서는 로컬 상태로만 관리하지만, 실서비스에서는 계정 단위로 저장할 수 있다.

| 컬럼 | 설명 |
| --- | --- |
| id | 설정 고유 ID |
| user_id | 사용자 ID |
| is_elderly | 어르신 여부 |
| with_child | 영유아 동반 여부 |
| disabled | 장애 여부 |
| outdoor_worker | 야외근로자 여부 |
| pregnant | 임산부 여부 |
| with_pet | 반려동물 동반 여부 |
| mobility_issue | 보행 불편 여부 |
| prefer_short_distance | 가까운 거리 우선 여부 |
| prefer_accessibility | 접근성 우선 여부 |

앱 연결: 홈 화면의 최적 쉼터 추천 점수와 추천 이유 태그에 반영한다.

### favorites

사용자가 저장한 즐겨찾기 쉼터를 관리한다.

| 컬럼 | 설명 |
| --- | --- |
| id | 즐겨찾기 고유 ID |
| user_id | 사용자 ID |
| shelter_id | 쉼터 ID |
| created_at | 즐겨찾기 등록 시각 |

앱 연결: 즐겨찾기 탭과 쉼터 상세 화면의 저장 상태에 사용한다.

### analysis_results

CSV 분석 결과 요약을 저장한다. 현재 `data-analysis/output/analysis_result.json`에 생성된 결과가 실서비스에서는 이 테이블로 저장될 수 있다.

| 컬럼 | 설명 |
| --- | --- |
| id | 분석 결과 고유 ID |
| period | 분석 기간 |
| region | 분석 지역 |
| risk_score | 종합 폭염 취약도 점수 |
| max_temperature | 평균 또는 대표 최고기온 |
| humidity | 평균 습도 |
| heatwave_days | 폭염일수 |
| heat_illness_cases | 온열질환자 수 |
| elderly_rate | 고령인구 비율 |
| summary | 분석 요약 |
| created_at | 분석 결과 생성 시각 |

앱 연결: 분석 탭의 지역별 위험도, 홈 위험도 카드, 추천 점수의 지역 위험도 가중치로 사용할 수 있다.

### api_cache

공공데이터 API 응답을 캐싱한다. 통합대피소 API, 기상특보 API, 생활기상지수 API처럼 외부 호출에 의존하는 데이터를 저장해 서비스 안정성을 높인다.

| 컬럼 | 설명 |
| --- | --- |
| id | 캐시 고유 ID |
| api_name | API 이름 |
| request_region | 요청 지역 |
| request_params | 요청 파라미터 |
| response_json | API 응답 원문 또는 정규화 결과 |
| fetched_at | 가져온 시각 |
| expires_at | 캐시 만료 시각 |

앱 연결: 지도 마커, 쉼터 후보, 현재 위험 안내, 기상특보 표시에서 API 장애 시 이전 데이터를 사용할 수 있게 한다.

## 앱 기능과 DB 연결 방식

| 앱 기능 | 연결 테이블 | 사용 목적 |
| --- | --- | --- |
| 홈 최적 쉼터 추천 | shelters, citizen_reports, user_preferences, analysis_results | 현재 위치, 쉼터 상태, 사용자 조건, 지역 위험도를 종합해 추천 |
| 지도 화면 | shelters, api_cache | 주변 쉼터 마커 표시와 API fallback |
| 쉼터 상세 | shelters, citizen_reports, favorites | 운영 상태, 제보 정보, 즐겨찾기 상태 표시 |
| 제보 기능 | citizen_reports | 실제 운영 상태와 혼잡도 보완 |
| 즐겨찾기 | favorites | 사용자 저장 쉼터 관리 |
| 맞춤 설정 | user_preferences | 추천 가중치 조정 |
| 분석 탭 | analysis_results | CSV 기반 폭염 위험 분석 결과 표시 |

## 시민 제보 데이터의 추천 활용

시민 제보는 공공데이터의 한계를 보완하는 핵심 데이터다. 통합대피소 API는 쉼터 위치와 기본 정보를 제공하지만, 실시간 혼잡도, 실제 냉방 상태, 접근성 문제, 위험 경로는 반영하기 어렵다.

실서비스에서는 최근 제보를 기준으로 다음과 같이 추천 점수를 보정할 수 있다.

- 운영 중 제보가 많으면 운영 여부 점수 증가
- 혼잡도 높음 제보가 많으면 추천 점수 감소
- 냉방 쾌적 제보가 많으면 냉방 상태 점수 증가
- 휠체어 접근 가능 제보가 많으면 접근성 점수 증가
- 위험 경로 제보가 있으면 해당 경로 또는 쉼터 추천 우선순위 감소

## API 캐시가 필요한 이유

통합대피소 API, 기상특보 API, 생활기상지수 API는 네트워크 상태, 호출 제한, 외부 서버 장애의 영향을 받을 수 있다. API 응답을 `api_cache`에 저장하면 다음 장점이 있다.

- API 장애 시 마지막 정상 데이터를 fallback으로 사용 가능
- 같은 지역 반복 요청을 줄여 응답 속도 개선
- API 호출 제한 초과 위험 감소
- 발표 또는 재난 상황에서 서비스 안정성 확보
- API 응답 원문과 정규화 결과를 비교해 데이터 품질 검증 가능

## 향후 DB 연결 순서

1. `shelters` 테이블을 먼저 연결해 통합대피소 API 데이터를 저장하고 지도 마커와 추천 후보로 사용한다.
2. `api_cache`를 추가해 통합대피소, 기상특보, 생활기상지수 API 응답을 안정적으로 관리한다.
3. `analysis_results`에 CSV 분석 결과를 저장해 홈과 분석 탭에서 공통으로 사용한다.
4. `citizen_reports`를 연결해 쉼터 상세 제보와 추천 점수 보정을 구현한다.
5. 로그인 도입 후 `user_preferences`와 `favorites`를 사용자 계정 단위로 저장한다.
6. 관리자 검수 기능을 추가해 쉼터 정보와 시민 제보의 신뢰도를 관리한다.

## 확장 방향

실서비스에서는 Supabase/PostgreSQL을 사용해 위 테이블을 구성할 수 있다. 초기에는 API 캐시와 쉼터 기본 정보부터 DB에 저장하고, 이후 사용자 계정 기반 기능이 필요해지는 시점에 맞춤 설정과 즐겨찾기 테이블을 연결하는 방식이 적절하다.

현재 MVP는 DB 없이도 추천 UX와 분석 근거를 시연할 수 있도록 구성되어 있으며, 이 문서는 실서비스 확장 시 필요한 데이터 구조를 정의하기 위한 설계 자료다.
